A1. Permisos y accesos

Síntesis de las herramientas de la categoría A1: el modelo de permisos de Linux, las claves SSH y las formas típicas en que un secreto queda a la vista. Da los conceptos y las herramientas, no la solución de cada challenge.

Modelo de usuarios y permisos de Linux

Cada archivo tiene un owner, un grupo y tres ternas de permisos rwx (lectura, escritura, ejecución) para owner, grupo y otros. En un directorio, r lista, w crea o borra entradas y x (execute o search) permite atravesarlo para llegar a lo de adentro: sin x en la carpeta no accedés a un archivo aunque el archivo te dé permiso. Se leen con ls -lah (la primera columna es el modo) y con stat (owner, permisos en octal y timestamps). id muestra tu uid, gid y grupos; whoami el usuario actual. La idea de fondo de toda la categoría es que el esquema de Linux es correcto pero la gente lo usa mal: permisos demasiado laxos, secretos dejados a la vista.

SSH y claves

SSH abre una shell remota autenticando por clave pública o por password. La clave privada se queda con el usuario y la pública va en el servidor, en ~/.ssh/authorized_keys. Para entrar con una clave, ssh -i <clave> -p <puerto> user@host, y ojo con el puerto, que el default 22 no siempre es el del challenge. SSH exige que la clave privada tenga permisos restrictivos (chmod 600) o se niega a usarla. scp -i <clave> -P <puerto> (P mayúscula) copia archivos entre máquinas por el mismo canal. Vale la pena poder hacer las dos cosas: saltar de un usuario a otro con ssh dentro de la propia VM, y bajar una clave a tu Kali con scp y entrar desde ahí.

Encontrar secretos mal guardados

Una clave privada ajena legible es una llave que podés usar. Para barrer homes y archivos ajenos sirven ls -lah /home/*, find / -name id_* 2>/dev/null y find / -perm -o=r para lo que es legible por todos. Los formatos de clave privada típicos son id_rsa, id_ecdsa e id_ed25519, texto que empieza con -----BEGIN ... PRIVATE KEY-----.

Secretos en procesos

Todo lo que pasa por la línea de comandos de un proceso es visible para cualquier usuario, porque los argumentos aparecen en /proc/<pid>/cmdline y en la salida de ps. Por eso pasar un password como argumento es inseguro. Las herramientas son ps aux o ps -ef (listan todos los procesos con su línea de comandos completa), ps -eo user,pid,args, y mirar /proc/<pid>/cmdline, donde los argumentos van separados por bytes nulos y se ven con tr '\0' ' ' < /proc/<pid>/cmdline. Un password encontrado así habilita ssh o su como ese usuario.

Cambiar de identidad: su y sudo

su <user> abre una shell como otro usuario, pidiendo el password de ese usuario. sudo ejecuta como otro usuario según lo que permita el archivo sudoers, y sudo -l lista qué te está permitido. Un sudoer que puede volverse otro usuario habilita el movimiento lateral: comprometer una cuenta y desde ella saltar a otras del mismo sistema. Ese encadenamiento, un password robado que compromete a un tercero, es el concepto central de A1.

ssh-agent y agent forwarding

El ssh-agent es un proceso que mantiene claves privadas desbloqueadas en memoria para no reescribir la passphrase cada vez. Se comunica por un socket cuya ruta está en la variable de entorno SSH_AUTH_SOCK, y el pid en SSH_AGENT_PID. Con ssh-add -l listás las claves cargadas y con ssh-add <clave> cargás una. El agent forwarding (ssh -A) reenvía ese socket a la máquina remota, así podés autenticarte a un tercer host usando una clave que nunca sale de tu máquina local. El riesgo es que si otro usuario en la VM puede leer el socket de tu agente (sabiendo el valor de SSH_AUTH_SOCK y teniendo permiso sobre ese archivo), puede pedirle firmas al agente y hacerse pasar por vos sin tener tu clave. Conceptos para investigar: variables de entorno de otro proceso (visibles en /proc/<pid>/environ), permisos del socket, y cómo ssh-add puede mitigar esto, con -c para pedir confirmación en cada uso y -t para ponerle un tiempo de vida a la clave.
