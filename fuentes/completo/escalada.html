Escalada de privilegios: sudo y setuid

La segunda categoría del laboratorio (B, privilegios) es un paso más allá de los permisos: acá el objetivo es hacer que un programa actúe con una identidad más poderosa que la tuya. Todas las técnicas (abuso de sudoers, shell escape, el bit setuid, PATH hijacking) comparten esa forma y su pregunta gemela de cómo se defienden. Son justo el tipo de mecanismo que cae en el quiz.

La base: identidad y permisos de un proceso

Todo proceso corre con una identidad (un usuario). El kernel guarda en realidad varios UIDs: el real UID (ruid, quién lanzó el proceso) y el effective UID (euid, con quién se chequean los permisos al abrir un archivo o matar un proceso). Normalmente coinciden, pero los mecanismos de escalada viven justo en la brecha entre los dos.

Effective UID (euid). El UID contra el que el kernel evalúa cada operación privilegiada del proceso. Si un programa logra correr con euid distinto (y mayor) que tu ruid, hace por vos cosas que vos no podés.

Sobre los archivos, los permisos son tres ternas (owner, group, other) de tres bits (read, write, execute). Dos consecuencias que se explotan seguido:

  • Ser dueño de un archivo no te deja leerlo si el bit de lectura del owner está en cero: el chequeo es siempre contra los bits, no contra "soy el dueño". Solo root (con CAP_DAC_OVERRIDE) los saltea.
  • Pero el dueño sí puede correr chmod sobre su archivo aunque no tenga permiso de leerlo: chmod se autoriza por ownership, no por los permisos actuales. Es una primitiva de escritura sobre los metadatos que habilita la de lectura.

La notación de chmod y el detalle del modelo de permisos octal están en el capítulo de permisos. Acá alcanza con recordar que chmod +r archivo agrega lectura para todos, y que un chmod lo puede hacer el dueño aunque no pueda leer el archivo.

Leer lo que sudo te permite

El ejemplo de sudo del threat model mostró la idea: en vez de dar root, el admin define en sudoers exactamente qué comando privilegiado puede correr cada usuario. Como atacante, el primer paso es siempre leer esa política:

sudo -l

La salida es críptica pero tiene un formato fijo. Cada línea es (usuario-destino) ETIQUETAS: /ruta/exacta/del/comando [argumentos]. Por ejemplo (bob) NOPASSWD: /bin/cat /home/bob/nota significa: podés correr ese cat, con ese argumento, como bob, sin contraseña. El -u de sudo elige el usuario destino: sudo -u bob /bin/cat /home/bob/nota.

Pensar en primitivas. De una lista de comandos permitidos, no todos sirven igual. Un atacante clasifica cada uno por la primitiva que da: leer un contenido (una primitiva de lectura), escribir en algún lado, o ejecutar código arbitrario. ls y stat solo dan metadata, sha1sum da un hash; el que devuelve el contenido tal cual (un cat) es la primitiva de lectura.

Wildcard abuse y path traversal

Cuando una regla usa un comodín, como /bin/cat /var/log/*, es tentador leerlo como "solo archivos de /var/log". No lo es: el * es un glob y sudo compara el string final del comando contra el patrón. Nada impide que el argumento arranque literalmente en /var/log/ y con .. salga a cualquier otro directorio:

sudo -u darleen /bin/cat /var/log/../../home/darleen/secreto
Path traversal. Usar .. (u otras formas de reescribir una ruta) para salir del directorio al que en teoría estaba acotado un acceso. Es una de las técnicas más frecuentes de la industria: la misma lógica está detrás de los LFI en aplicaciones web y del zip slip.
Un comodín en sudoers no es un sandbox de directorio. Es un match de texto contra el comando final. Cualquier * es candidato a wildcard abuse, y cualquier comando que reciba una ruta como argumento es candidato a path traversal si esa ruta no se normaliza y valida antes de usarla.

Shell escape (GTFOBins)

Muchos programas "inocentes" e interactivos tienen una función legítima para lanzar un comando de shell sin salir: less y vi con !comando, man, awk, find, tar, ftp. Si sudoers te deja correr uno de esos como otro usuario, el shell que abrís hereda esa identidad, aunque sudo -u gaia /bin/bash esté prohibido.

La idea concreta. sudo -u gaia /usr/bin/less /home/gaia/manifiesto corre less como gaia. Dentro, !sh (o !cualquier-comando) abre una subshell que también corre como gaia. Desde ahí ya ejecutás lo que quieras con esa identidad.

El catálogo de referencia de estas técnicas es GTFOBins: para cada binario lista cómo abusar de él (shell, lectura de archivos, escritura, escalada vía sudo o setuid).

El bit setuid

El bit setuid (la s en la posición de ejecución del owner, un permiso 4755 que se ve -rwsr-xr-x) hace que al ejecutar el binario, el proceso tome como euid al dueño del archivo, no a quien lo lanza. Es el mecanismo con el que un programa de bob puede leer un archivo de bob aunque lo corra alice.

Ser dueño de un binario no otorga nada por sí solo. Sin el bit s, un programa de bob que corre alice tiene euid alice y falla. El s convierte "soy dueño de este programa" en "quien lo corre actúa como yo". Por eso, para encontrar el binario útil, se filtra por dueño y por el bit setuid: find / -user bob -perm -4000 2>/dev/null.

PATH hijacking de un setuid

Si el binario setuid, en su código, ejecuta a otro programa por nombre y no por ruta absoluta, la víctima elige el programa que se ejecuta. Esto pasa cuando usa system("prog ...") (que siempre lanza /bin/sh -c) o execlp/execvp (la p = "resolver el nombre recorriendo $PATH"). Como $PATH lo controla el atacante, se puede anteponer un directorio con un ejecutable propio que se llame igual:

# el setuid hace, por dentro:  execlp("stat", "stat", argv[1], NULL)
echo '#!/bin/bash'                  >  /tmp/stat
echo '/ruta/al/programa/que/quiero' >> /tmp/stat
chmod +x /tmp/stat
export PATH=/tmp:$PATH              # nuestro directorio primero
which stat                          # debe devolver /tmp/stat
/ruta/al/binario_setuid  argumento  # resuelve "stat" -> nuestro script
El escollo del shebang. Si el programa intermediario es un script #!/bin/bash, el kernel mete un /bin/bash en el medio, y bash al arrancar con euid distinto de ruid baja el euid a ruid por seguridad: el privilegio heredado se pierde. Se resuelve pidiéndole que no lo haga, con #!/bin/bash -p (modo privilegiado), o haciendo que el intermediario sea un binario compilado (sin bash de por medio).

Utilidades estándar con bit setuid

Un caso especialmente peligroso es una utilidad conocida instalada como setuid de otro usuario. Muchas tienen features para ejecutar otro programa, y el cómo lo hacen decide si sirven:

UtilidadFeature que ejecuta otro comandoHereda el euid?
find-exec cmd {} \; (corre cmd por cada resultado)Sí: find hace exec directo, sin shell.
tar--checkpoint-action=exec=... o --to-command=...Depende: si mete un shell, ese shell puede resetear el euid.

Por eso find suele ser el camino fácil (ejecuta el comando él mismo y conserva el euid del proceso) mientras que tar exige rodeos: si termina lanzando un /bin/sh, se cae en el mismo reseteo de privilegios del shebang.

Cómo se defiende cada una

La pregunta gemela del quiz siempre es cómo evitar el abuso. En una línea por técnica:

TécnicaDefensa
Wildcard / path traversal en sudoersNo usar comodines amplios; acotar a rutas exactas y normalizar/validar la ruta antes de abrirla (rechazar ..).
Shell escapeNo dar por sudo binarios con capacidad de lanzar shells; preferir un wrapper mínimo que haga solo la acción necesaria.
PATH hijacking de un setuidInvocar siempre por ruta absoluta (nunca system/execvp); sanitizar el entorno (resetear $PATH e IFS); droppear privilegios (setuid(getuid())) antes de ejecutar si no se necesitan.
Utilidad estándar como setuidNo instalar utilidades potentes con el bit setuid; dar la capacidad justa (capabilities acotadas), no el poder genérico de find/tar como otro usuario.

Todo esto es el mismo patrón del threat model: confianza mal ubicada en un boundary (el entorno, el $PATH, un socket, un comodín) y falta de mínimo privilegio. La metodología para encontrar estas grietas es la de la clase de ofensiva: recon (leer permisos y sudoers), buscar la primitiva, y usar cada abuso como habilitador del siguiente.

Preguntas típicas de este tema. Diferencia entre real UID y effective UID, y por qué un binario setuid corre con el euid del dueño. Por qué el dueño de un archivo con cero permisos igual puede leerlo tras un chmod pero no antes. Leer una línea de sudo -l e identificar qué primitiva da cada comando permitido. Por qué un * en sudoers no limita el directorio (wildcard abuse y path traversal). Cómo funciona un shell escape y con qué binarios. Cómo funciona el PATH hijacking de un setuid y cómo se lo arregla (ruta absoluta, sanear entorno, droppear privilegios). Por qué find conserva el euid y un intermediario de bash lo pierde (el shebang y -p).
